# notesd — Architecture Specification

## 1. Overview

A self-hosted note-taking system: one Go executable backed by SQLite serves an online-only React web client and syncs with offline-first native iOS and Android apps. V1 targets a single owner with multiple devices.

| Area | Decision |
| --- | --- |
| Backend | Single Go executable, SQLite (WAL) with FTS5; no external infrastructure |
| Web | React + TypeScript + Tiptap, embedded in the binary; requires a server connection |
| Mobile | Native Swift and Kotlin apps with local SQLite + FTS5; fully usable offline |
| Documents | Whole Markdown documents in a restricted CommonMark + GFM dialect |
| Sync | State-based incremental replication using per-note revisions and a global change sequence |
| Conflicts | Field-level auto-merge when safe; otherwise a conflict copy |
| Deletion | Permanent tombstones so stale devices cannot resurrect notes |
| Search | FTS5 on every platform, title-weighted BM25 |
| Reliability | Transactional writes, idempotent mutations, crash-safe sync, consistent backups |

## 2. Scope and Requirements

### 2.1 Notes

| Field | Description |
| --- | --- |
| ID | Generated by the client so notes can be created offline; UUIDv7 recommended for chronological ordering |
| Title | Plain text, one line. Editors present it as the first line of the document (Apple Notes style); it is stored and merged as its own field |
| Content | Markdown document |
| Created at / Updated at | Unix milliseconds, UTC; informational only, never used to order sync |
| Revision | Assigned by the server |
| Deleted at | Optional deletion timestamp |

### 2.2 Editing

Users edit in a WYSIWYG editor and never see Markdown syntax. V1 supports plain text, bold, italic, strikethrough, headings (H1–H3), bulleted and numbered lists, checklists, links and blockquotes. Images, attachments and tables are deferred.

### 2.3 Search

- Full-text search over titles and content, with title matches prioritized.
- Case-insensitive, accent-insensitive where supported, prefix matching for search-as-you-type.
- Results show highlighted excerpts; search works offline on mobile.

### 2.4 Synchronization

Sync runs automatically (in the background where the OS allows), resumes after interruptions, tolerates long offline periods, and is idempotent. It must detect concurrent edits and preserve both sides, never resurrect deleted notes, minimize requests and payloads, and never depend on device clocks.

### 2.5 Web application

The web app offers full note management, editing and search, but needs a live server connection. It may hold unsaved edits in memory through transient failures; nothing persists across browser restarts.

### 2.6 Non-functional requirements

- **Performance:** low idle CPU and memory; thousands to tens of thousands of notes on ordinary hardware. Targets come from benchmarks, not estimates.
- **Reliability:** tolerate server crashes and restarts, network loss, incomplete, duplicate or out-of-order requests, app termination, and devices offline for long periods. Committed SQLite transactions survive process crashes; disk failure or corruption requires a backup.
- **Deployment:** one executable plus a data directory; no separate frontend process. Docker images are optional, never required.

### 2.7 Non-goals for V1

| Excluded | Reason |
| --- | --- |
| Real-time collaboration, CRDTs, WebSockets | One active editor per note; HTTP sync is sufficient |
| Web offline mode | Would add a browser replica and a second sync engine |
| Full version history, automatic Markdown merge | Not needed to preserve conflicts; formatting-aware merging is complex |
| Images and attachments | Need their own binary storage and sync design |
| Multi-user collaboration, end-to-end encryption | Add authorization complexity; E2EE breaks server-side search |
| PostgreSQL, Redis, external search, job workers, Kubernetes | Unnecessary at this scale |

## 3. Architecture

Three clients talk HTTPS/JSON to one Go server. Only the native apps keep a local replica; the web client calls the API directly.

&#91;embedded content: system architecture · 3 clients, 1 server\]

Every client reaches the server over HTTPS/JSON; the Go binary also serves the web app's build, and only the native apps keep working without a connection.

### 3.1 Responsibilities

| Component | Responsibilities |
| --- | --- |
| Go server | Authentication; note CRUD; revision validation and conflict detection; global change sequence; incremental sync; full-text search; serving the web app; database maintenance and backups. Stores whole Markdown documents and never interprets edits. |
| Native clients | Rich-text editing; local persistence and search index; recording pending changes; background sync; conflict resolution; local deletion state; connectivity and sync status. The editor only reads and writes local data; sync runs independently. |
| Web client | Authentication; note listing and navigation; editing with debounced autosave; search; conflict handling; connection and error status. No local database or sync engine. |

### 3.2 Technology stack

| Platform | Stack |
| --- | --- |
| Backend | Go, `net/http`, SQLite (WAL) + FTS5, JSON over HTTPS, structured logging, web assets via `embed`, systemd or equivalent |
| iOS | Swift, SwiftUI, `UITextView`/TextKit editor via `UIViewRepresentable`, SQLite + FTS5, URLSession, iOS background tasks |
| Android | Kotlin, Jetpack Compose with Navigation 3 (list and note side by side from 600dp, split around a foldable's hinge), `EditText`/`Spannable` editor via `AndroidView`, bundled SQLite + FTS5 (`androidx.sqlite`), OkHttp, WorkManager |
| Web | TypeScript, React, Tiptap/ProseMirror, Vite, lightweight CSS; Node.js only for building |

Native apps use platform controls for selection, keyboard, context menus and formatting. Pick the server's SQLite driver for portability, transaction behaviour and build simplicity, and avoid unnecessary frameworks.

## 4. Data Model

The server holds the authoritative latest state of each note, not a full edit history; mobile devices hold complete replicas plus sync metadata. Two counters must never be confused: the **revision** advances when one note changes, the global **change sequence** advances when any note changes.

### 4.1 Server schema

```sql
CREATE TABLE notes (
    seq         INTEGER PRIMARY KEY,         -- stable rowid; keys the FTS index
    id          TEXT    NOT NULL UNIQUE,     -- client-generated
    title       TEXT    NOT NULL DEFAULT '',
    content     TEXT    NOT NULL DEFAULT '', -- Markdown
    revision    INTEGER NOT NULL DEFAULT 1,
    change_seq  INTEGER NOT NULL,            -- server-assigned
    created_at  INTEGER NOT NULL,            -- Unix ms, UTC
    updated_at  INTEGER NOT NULL,
    deleted_at  INTEGER,                     -- tombstone marker
    conflict_of TEXT                         -- original note, for conflict copies
);
CREATE UNIQUE INDEX idx_notes_change_seq ON notes(change_seq);
CREATE INDEX idx_notes_updated_at ON notes(updated_at DESC, id DESC) WHERE deleted_at IS NULL;

CREATE TABLE sync_state (
    id          INTEGER PRIMARY KEY CHECK (id = 1),
    current_seq INTEGER NOT NULL DEFAULT 0,
    generation  TEXT    NOT NULL             -- sync generation ID (§11.4)
);

-- Tags in live notes (§7.5), kept with the search index.
CREATE TABLE note_tags (note_seq INTEGER REFERENCES notes(seq), key TEXT, name TEXT, PRIMARY KEY (note_seq, key));

-- Server-wide settings from the apps: the Resend key and sender for emailing notes.
CREATE TABLE settings (key TEXT PRIMARY KEY, value TEXT NOT NULL);

CREATE TABLE applied_operations (
    operation_id  TEXT PRIMARY KEY,
    request_hash  TEXT    NOT NULL,
    response_json TEXT    NOT NULL,          -- status code and body, replayed verbatim
    applied_at    INTEGER NOT NULL
);

-- Single owner account and its sessions (§10); only token hashes are stored.
CREATE TABLE users (id INTEGER PRIMARY KEY CHECK (id = 1), username TEXT, password_hash TEXT, created_at INTEGER, updated_at INTEGER);
CREATE TABLE sessions (id TEXT PRIMARY KEY, kind TEXT, name TEXT, access_hash TEXT UNIQUE, access_expires_at INTEGER,
                       refresh_hash TEXT UNIQUE, refresh_expires_at INTEGER, csrf_token TEXT, created_at INTEGER, last_used_at INTEGER);
```

`notes` has an explicit `INTEGER PRIMARY KEY` rather than relying on the implicit rowid, because `VACUUM` can renumber implicit rowids and silently desynchronize the search index. Migrations are numbered SQL files applied at startup and tracked in `PRAGMA user_version`. The full schema is `server/migrations/`.

Every mutation, including deletion, increments the note's revision and `current_seq`, updates the search index and records its operation in a single transaction. All writes go through one connection with `BEGIN IMMEDIATE`, so concurrent requests queue in the server instead of failing with `SQLITE_BUSY`; reads use a separate pool and never block on writes. A transactional counter keeps sync cursors aligned with commit order.

### 4.2 Idempotent mutations

Clients attach a unique operation ID to each mutation so retries after a lost response are safe. For each request the server:

1. Looks up the operation ID. If found, it checks the request hash and returns the stored response; a reused ID with a different payload is rejected.
2. Otherwise it validates and applies the mutation, storing the ID and response in the same transaction.

V1 retains operation records indefinitely; expiring them needs an explicit protocol, since clients may retry at any time.

### 4.3 Mobile schema

As built on Android (`apps/android/core/src/main/resources/migrations`); iOS follows the same shape.

```sql
CREATE TABLE notes (
    seq               INTEGER PRIMARY KEY, -- stable rowid, keys notes_fts
    id                TEXT NOT NULL UNIQUE,
    title             TEXT NOT NULL DEFAULT '',
    content           TEXT NOT NULL DEFAULT '',
    created_at        INTEGER NOT NULL,
    updated_at        INTEGER NOT NULL,
    deleted_at        INTEGER,
    conflict_of       TEXT,             -- the note a conflicted copy was split from
    server_revision   INTEGER,          -- revision local edits are based on; NULL for new offline notes
    server_change_seq INTEGER,
    dirty             INTEGER NOT NULL DEFAULT 0,  -- unsynced changes pending
    base_title        TEXT,             -- last synced version, kept while edits are pending
    base_content      TEXT,
    base_deleted_at   INTEGER,
    full_sync_seen    INTEGER NOT NULL DEFAULT 0  -- reached by the current full reconciliation
);

CREATE TABLE sync_outbox (
    operation_id   TEXT PRIMARY KEY,
    note_id        TEXT NOT NULL,
    operation_type TEXT NOT NULL,
    base_revision  INTEGER,
    payload_json   TEXT NOT NULL,
    created_at     INTEGER NOT NULL,
    sent           INTEGER NOT NULL DEFAULT 0  -- frozen once sent
);

CREATE TABLE sync_state (               -- one row
    cursor       INTEGER NOT NULL DEFAULT 0,
    generation   TEXT,                  -- NULL before the first sync
    full_sync    INTEGER NOT NULL DEFAULT 0, -- a full reconciliation is in progress (§11.4)
    last_sync_at INTEGER,
    last_error   TEXT
);
```

Outbox rules:

- A local edit, its dirty flag and its outbox entry are written in one transaction.
- Unsent operations for the same note may be coalesced into one update.
- Once sent, an operation's ID, payload and base revision are frozen across retries. New edits queue as a separate operation until it is acknowledged; it carries the base revision it had when it was first sent, never rewritten afterwards.

### 4.4 Search index

```sql
CREATE VIRTUAL TABLE notes_fts USING fts5(
    title,
    body_text,
    tokenize = 'unicode61 remove_diacritics 2'
);
```

- Holds the plain-text title and text extracted from the Markdown; in V1 the FTS rowid equals the `notes` rowid.
- Kept consistent through triggers or repository code in the same transaction; deleted notes are removed.
- Derived data that can be rebuilt from `notes`. Mobile clients keep equivalent indexes.
- FTS5 availability and identical tokenizer behaviour must be verified on iOS and Android.

## 5. Synchronization Protocol

Notes sync as whole documents over HTTPS/JSON: clients push edits tagged with a base revision and pull changes after a cursor. No keystrokes, editing operations, CRDT updates or persistent connections are exchanged; whole-document sync suits small personal notes with one active editor and is easy to debug.

### 5.1 Uploading changes

On mobile an edit is saved to local SQLite, marked dirty and added to the outbox; the UI updates immediately and the sync engine submits it later.

```http
PUT /api/v1/notes/019a1234

{ "operationId": "019b5678", "baseRevision": 5,
  "title": "Shopping List", "content": "- Milk\n- Bread\n- Eggs" }
```

- **Base revision is current** → `{ "id": "019a1234", "revision": 6, "changeSeq": 105, "updatedAt": …, "status": "updated" }`, and the client acknowledges the operation locally. Identical content answers `"status": "unchanged"` without a new revision.
- **Base revision is stale** → `409 Conflict` with `{ "error": "revision_conflict", "current": { …latest note… } }`, and the client resolves it as described in section 6. Two more conflict codes use the same shape: `note_deleted` (the note is a tombstone; `current` carries `deletedAt`) and `note_exists` (a create reusing an ID, including a deleted one).
- **Operation already applied** → the stored response, with the header `Idempotent-Replayed: true`. The same operation ID with a different payload is `422 operation_id_reused`.

### 5.2 Downloading changes

```http
GET /api/v1/sync?since=100&limit=100
```

At the start of the request the server captures a high-water mark `H` from `current_seq`, then reads within one snapshot:

```sql
SELECT * FROM notes
WHERE change_seq > :since AND change_seq <= :H
ORDER BY change_seq
LIMIT :limit;
```

The response holds the latest state of each changed note (intermediate revisions are skipped; tombstones carry `deletedAt`), plus `nextCursor`, `hasMore` and the server's `generation` (§11.4). Clients send their stored generation back as `?generation=`; a mismatch, or a cursor beyond anything the server issued, answers `409` (`generation_mismatch` / `cursor_ahead`) and the client runs a full reconciliation.

Cursor rules:

1. The client applies a page, preserves any conflicting unsynced edits, and persists the new cursor in the same local transaction before requesting the next page.
2. A crash before commit simply re-downloads the page; duplicate downloads are harmless.
3. When no more changes exist, the server may advance the cursor to `H`, but it must never return a cursor that skips a committed change missing from the response.
4. Sequence increments and note writes commit atomically, so clients never see a sequence number without its note state.

### 5.3 Edits during an upload

An acknowledgment applies to the submitted operation only, never to the current local contents. If the user produces version B while version A is in flight, B stays pending after A is acknowledged, rebased on A's new revision, and A becomes the note's base (`base_title`, `base_content`), so a later merge doesn't mistake A's changes for a conflict. Uploads are serialized per note; different notes sync independently.

An editor open on a note while sync changes it shows the change at once if nothing is being typed; otherwise its next save passes the stored version the typing grew from, and the store merges the two as in §6.1.

### 5.4 Initial sync

A new device authenticates, initializes its database, syncs from cursor 0 in pages, builds its search index and persists the cursor. Notes appear as they arrive, and the process resumes if interrupted.

### 5.5 Scheduling

- Triggers: app launch, return to foreground, local edits (debounced), connectivity regained, OS-approved background windows, periodic refresh while active.
- Failures back off exponentially with jitter; edits never cause one request per keystroke.
- Background execution is not guaranteed on iOS or Android, so correctness must never depend on its timing.

## 6. Conflicts and Deletion

Accept an edit when its base revision is current, merge automatically when there is no ambiguity, and otherwise keep both versions. Unsynced changes are never silently discarded.

### 6.1 Field-level merge

Title and content are merged independently by comparing base, local and server values. A field changed on only one side takes that side's value; a field changed identically on both sides is already resolved. Content is compared in canonical serialized form, so another client's formatting style (`* item` versus `- item`) does not count as a change. The client submits the merged note against the new server revision and repeats if the server moves again.

| Field | Base (rev 5) | Local | Server (rev 6) | Merged (rev 7) |
| --- | --- | --- | --- | --- |
| Title | Shopping | Groceries | Shopping | Groceries |
| Content | Buy milk | Buy milk | Buy oat milk | Buy oat milk |

### 6.2 Conflicting content

When both sides changed the content differently, V1 does not merge text. The server version keeps the original note; the local version becomes a new note titled `<Title> (Conflicted copy)` with a new UUID and optional `conflictOf: <original id>` metadata. It then behaves like any other note.

The native apps make the copy automatically and say so (a notice, and a banner on the copy linking to the original), since sync runs in the background with no one to ask. The web app saves interactively and asks the user instead.

Three-way Markdown merging is deferred: it must handle formatting syntax, lists, links and document structure.

### 6.3 Crash-safe conflict handling

Creating a conflict copy, adding its creation to the outbox and updating the original note's sync state commit as one local transaction. A crash before commit leaves the original pending edit recoverable.

### 6.4 Tombstones

Deletion keeps a tombstone (ID, revision, change sequence, deletion timestamp) instead of removing the row; the title and content are cleared. Deleting an already deleted note succeeds (`already_deleted`) without a new revision, whatever base revision the client sends. It increments the revision and change sequence and syncs like any other change. V1 keeps tombstones indefinitely, so the server never tracks per-device acknowledgment and devices offline for months sync normally.

| Situation | Outcome |
| --- | --- |
| Deleted elsewhere, local copy unmodified | Client marks it deleted; the old copy is never re-uploaded |
| Deleted elsewhere, edited offline | Server rejects the edit and the tombstone stands; the edits become a new note titled `<Title> (Recovered copy)` |
| Deleted offline, edited elsewhere | Server rejects the stale deletion; the newer note is kept and the deletion intent is recorded for the user to resolve (Android: the note reappears with a notice that it changed elsewhere) |

### 6.5 Trash (proposed)

A 30-day Trash is recommended but not final. Because tombstones clear content today, adopting Trash means deletion must keep the content until the purge. If adopted, deletion moves a note to Trash, it can be restored while retained, its content is purged after 30 days, and its tombstone stays forever; only then is a scheduled cleanup needed. The alternative for V1 is immediate logical deletion with permanent tombstones.

## 7. Document Format and Editing

Markdown is the stored format for portability and readability; editors work on a native in-memory model and serialize back to Markdown only on autosave, never per keystroke.

### 7.1 Markdown dialect

A restricted, documented dialect based on CommonMark with selected GitHub Flavored Markdown extensions: paragraphs and line breaks, headings, bold, italic, strikethrough, links, ordered and unordered lists, task lists and blockquotes. It is implemented identically on iOS, Android and web. Unsupported constructs must not be silently discarded; V1 editing and import may be limited to the subset.

Unsupported constructs (code spans and fences, tables, images, horizontal rules, raw HTML, and anything else outside the subset) are kept as opaque raw blocks or raw inline runs: shown read-only, not editable, and written back byte-for-byte on save. Turning them into ordinary text is not enough. The serializer would escape their syntax characters and fold their line breaks, so one save on any client would corrupt a note written elsewhere (for example a code fence pasted on another device).

### 7.2 Editing model

Markdown is parsed once into the native model (TextKit attributed strings on iOS, spans on Android, ProseMirror on web) and serialized during autosave. Editing must preserve cursor position, selection, undo/redo and active IME composition; saving never rebuilds the editor UI or resets the selection.

The editor document is `title block+`: the note's title is its first line, unformatted and single-line, and the rest is the body. On save the title line becomes the `title` field and the body is serialized to `content`, so the stored note, the sync protocol and the per-field merge are the same on every client. The web app implements this; the native editors follow the same model.

### 7.3 Autosave

- **Native:** debounced local saves, flushed on lifecycle events, keeping the gap to durable persistence short enough to survive abrupt termination. The local database and outbox stay consistent.
- **Web:** debounced HTTP saves, serialized per note so responses cannot arrive out of order.
- **UI states:** unsaved changes, saving, saved, save failed, conflict detected.

### 7.4 Cross-platform consistency

Serialization rules are shared and deterministic for app-produced documents, for example always `**bold**` rather than `__bold__`, and one task-list syntax. Hard line breaks are written as a backslash before the newline (CommonMark), never as two trailing spaces, which editors and tooling routinely strip; serialized output has no trailing whitespace. A shared fixture suite checks semantic round-trip stability across all three editors; byte-for-byte preservation of imported Markdown is not a goal.

Lists, checklists, paragraph styles, cursor behaviour and serialization need substantial custom engineering on top of native text components, so the native editors are prototyped first.

### 7.5 Tags

Tags are plain text in the note, as in Bear: there is no tag field, so tags sync, merge and conflict with the text that holds them, and no protocol or document-format change is needed. Every platform derives them with the same extractor, pinned by `shared/markdown-fixtures/tags.json`; editors only style them.

- **Syntax:** `#tag`, or `#multi word tag#` closed by a `#` that follows a non-space and ends a word. `/` nests to any depth: `#home/repairs`, `#school projects/biology 101#`.
- **Where:** the title (plain text) and every body line except fenced code. A tag starts at the beginning of a line or after whitespace, `(`, `[` or `{`; `# Heading` is a heading, `C#` and URL fragments are not tags. Code spans, links, images and autolinks never hold tags; emphasis does not interrupt them.
- **End:** a one-word tag ends at whitespace or punctuation other than `-`, `_` and `/` (`#one,` is `one`). A multi-word tag stays on one line.
- **Numbers:** a one-word tag made only of digits, `-`, `_` and `/` is not a tag (`#1 priority`); `#2024#` is.
- **Identity:** levels are trimmed, inner spaces collapsed and empty levels dropped; the key is the result lowercased. A note lists each key once, with its first spelling; across notes, a tag is named as in the most recently updated note using it.
- **Hierarchy:** `#a/b` implies `a`. Filtering by a tag includes its nested tags; counts are distinct notes.
- **Lifetime:** a tag exists while a live note uses it.

Renaming and deleting tags (rewriting every note) are not implemented yet.

## 8. Search

Every platform uses SQLite FTS5: mobile searches its local database with no network, and the web app calls `GET /api/v1/search` on the server.

### 8.1 Indexed content

The index holds titles and plain text extracted from Markdown, so formatting never affects results (`This is **important**.` is indexed as `This is important.`). Extraction preserves word boundaries and follows the same rules on server and mobile, checked with shared fixtures. Each note mutation updates the index in the same transaction, and the index can be rebuilt from the notes table without touching sync state. Tags (§7.5) are indexed alongside, in `note_tags`. A migration that changes derived data asks for a rebuild, which the server runs at startup.

### 8.2 Ranking

BM25 with per-column weights, title 10.0 and content 1.0:

```sql
SELECT n.id, n.title,
       snippet(notes_fts, 1, '<mark>', '</mark>', '…', 20) AS excerpt
FROM notes_fts
JOIN notes n ON n.rowid = notes_fts.rowid
WHERE notes_fts MATCH ?
  AND n.deleted_at IS NULL
ORDER BY bm25(notes_fts, 10.0, 1.0)
LIMIT 30;
```

This weights relevance rather than forcing every title match above every content-only match. If strict title-first ordering is required, add an explicit title-match tier.

### 8.3 Queries and results

- Results update as the user types, with a short debounce and FTS5 prefix queries.
- FTS5 queries are built safely from user input and parameterized, never interpolated; malformed syntax never surfaces as a user-visible error.
- Each result returns `id`, `title`, a highlighted `excerpt` and `updatedAt`; deleted notes are excluded and the server caps result counts. The server's excerpt is HTML-safe: note text is escaped and matches are wrapped in `<mark>`, so the web app can render it directly.
- Query building is uniform: the input is split into words, each becomes a quoted prefix term, and terms are ANDed. FTS5 operators in user input are inert.
- On mobile, results reflect local edits immediately, before they sync.

## 9. API

A versioned JSON API under `/api/v1` with standard HTTP status codes, authentication on every note endpoint, and optimistic concurrency on every mutation.

| Method | Endpoint | Purpose |
| --- | --- | --- |
| `GET` | `/api/v1/auth/status` | Whether first-run setup is still required |
| `POST` | `/api/v1/auth/setup` | Create the owner account with the setup token |
| `POST` | `/api/v1/auth/login` | Authenticate (`client: "web"` or `"device"`) |
| `POST` | `/api/v1/auth/refresh` | New device access token from a refresh token |
| `POST` | `/api/v1/auth/logout` | End a session |
| `GET` | `/api/v1/auth/session` | Current session (and the CSRF token, for browsers) |
| `POST` | `/api/v1/auth/password` | Change the password; signs out every other session |
| `GET` | `/api/v1/auth/sessions` | List signed-in browsers and devices |
| `DELETE` | `/api/v1/auth/sessions/:id` | Revoke a session |
| `GET` | `/api/v1/notes` | List notes (paginated), with `total`; `?tag=` or `?untagged=true` filters |
| `GET` | `/api/v1/notes/:id` | Retrieve a note (`410` with the tombstone if deleted) |
| `POST` | `/api/v1/notes` | Create a note |
| `PUT` | `/api/v1/notes/:id` | Update a note |
| `DELETE` | `/api/v1/notes/:id` | Delete a note |
| `POST` | `/api/v1/notes/:id/email` | Email the note as stored, through Resend |
| `GET` `PUT` `DELETE` | `/api/v1/settings/email` | The Resend API key (write-only) and sender |
| `GET` | `/api/v1/sync` | Download changes |
| `GET` | `/api/v1/search` | Search notes; same filters as listing |
| `GET` | `/api/v1/tags` | Tags in live notes, with counts |
| `GET` | `/healthz` | Process health |
| `GET` | `/readyz` | Database readiness |

- Create, update and delete accept operation IDs for retry-safe mutations.
- Validation errors, authorization failures and revision conflicts use clear, consistent response shapes.
- Note listing (`?limit=50`) returns list fields only: ID, title, created and updated timestamps, revision and a plain-text preview (one line per block, at most 160 characters). Mobile apps build lists locally.
- Errors share one shape: `{ "error": code, "message"?, "field"?, "current"? }`.
- The authoritative, up-to-date reference is `server/README.md`; the OpenAPI document in `shared/api/` is still to be written.
- Listing and sync use cursor pagination; sync cursors are based only on server-assigned sequences, never offsets.
- Search queries are parameterized, validated, limited and paginated.
- Emailing sends the server's copy, not the client's: the request carries the revision the client shows, and a different one is `409 stale_revision`, so the client syncs first and the email matches what the sender saw. Browsers can't call Resend directly, and one key serves every device.
- Major versions are explicit. Mobile apps may stay outdated for long periods, so breaking changes to note format, sync semantics or authentication need a compatibility strategy.

## 10. Security

V1 is a single-user installation: one owner account, signed in from multiple devices, with no sharing, authorization rules or multi-tenant isolation.

- **Credentials:** username and password, hashed with Argon2id (parameters encoded in the hash so they can be raised later); never stored in plaintext. Password changes are supported and sign out every other session. Failed logins are rate-limited (10 per 15 minutes per client address).
- **First run:** while no owner exists, the server logs a one-time setup token at startup, and a setup link (`<public URL or listen address>/setup#<token>`) that opens the web onboarding with the token filled in; the fragment keeps the token out of request and proxy logs. Creating the account through onboarding requires the token; it changes on every start unless `NOTESD_SETUP_TOKEN` fixes it. The alternative, `notesd create-owner`, needs shell access to the data directory. Either way an unauthenticated stranger cannot claim a fresh instance.
- **Web sessions:** an HttpOnly, SameSite=Lax cookie (`Secure` and `__Host-` prefixed when `--public-url` is https) with a 30-day sliding expiry, plus a CSRF token the web app keeps only in memory and sends as `X-CSRF-Token` on every mutation; cross-origin `Origin` headers are rejected.
- **Mobile sessions:** a one-hour access token and a 180-day sliding refresh token, sent as bearer tokens and kept in the iOS Keychain or Android Keystore-backed storage. Refresh tokens are not rotated, so a refresh whose response is lost can be retried; revocation deletes the session. Only token hashes are stored server-side. Session expiry affects sync only, never access to local notes.
- **Transport:** HTTPS for any remote access; TLS may terminate at any common reverse proxy. Private-network and VPN-only installations are supported.
- **Encryption:** no at-rest or end-to-end encryption in V1; users may rely on disk encryption. Documentation must state that the server can read note content. End-to-end encryption affects search, authentication and the data model, so it is a separate future decision.

## 11. Deployment and Operations

Production needs one executable, a writable data directory and an open HTTP port; schema migrations run automatically at startup.

### 11.1 Running the server

```text
notesd
data/
    notes.db
    notes.db-wal   # runtime file, may not exist
    notes.db-shm   # runtime file, may not exist
```

```bash
./notesd --data-dir /var/lib/notesd --listen 127.0.0.1:8080
```

Configuration is flags and environment variables (`NOTESD_DATA_DIR`, `NOTESD_LISTEN`, `NOTESD_PUBLIC_URL`, `NOTESD_LOG_LEVEL`, `NOTESD_LOG_FORMAT`, `NOTESD_SETUP_TOKEN`, and `NOTESD_RESEND_URL` for tests); a config file is not planned unless the option count grows. Subcommands: `create-owner`, `reset-password`, `reindex` (rebuild the search index), `check` (integrity check), `version`; `backup` is still to be built (§11.4). Targets: Linux x86-64 and ARM64 (including Raspberry Pi 5), small VPS installs and home servers. Docker images are optional.

WAL mode is enabled with a busy timeout for brief write contention. The development toolchain and build tasks are defined in the root `mise.toml` (`mise run build` produces the binary with the web app embedded). Installation, HTTPS and systemd are covered for users in `docs/hosting.md`; releases (server binaries and the signed APK) in `docs/releasing.md`.

### 11.2 Process supervision

systemd is recommended. The server shuts down gracefully on termination signals so transactions complete or roll back.

```ini
[Unit]
Description=notesd
After=network.target

[Service]
Type=simple
User=notesd
Group=notesd
ExecStart=/usr/local/bin/notesd --data-dir /var/lib/notesd
Restart=on-failure
RestartSec=5
StateDirectory=notesd

[Install]
WantedBy=multi-user.target
```

### 11.3 Self-healing

| Failure | Recovery |
| --- | --- |
| Server crash or unclean shutdown | Supervisor restarts it; SQLite rolls back incomplete writes and startup proceeds normally |
| Network loss | Apps keep working offline; pending changes stay in SQLite and retry with idempotent operation IDs |
| Interrupted sync | Cursor advances only after changes are applied; sync restarts from the last committed cursor |
| Database corruption | `PRAGMA integrity_check` via an admin command; failures logged clearly; the database is never deleted or replaced automatically |

### 11.4 Backups and disaster recovery

Client replicas are not a backup. `notesd backup /path/to/backup.db` uses SQLite's online backup API or an equivalent consistent snapshot; copying the live file under WAL is not safe. Backups plug into restic, Borg, systemd timers, NAS jobs or object storage, and off-device copies are strongly recommended.

Restoring an older backup leaves clients with newer revisions and cursors than the server. The server therefore keeps a persistent **sync generation ID**, which clients store with their cursor. When it changes, clients run a full reconciliation instead of incremental sync, preserving unsynced edits and never treating missing notes as deleted. Status: the generation exists in `sync_state`, is returned on every sync page and is checked when sent back; changing it on restore (and the `backup` command itself) is still to be built and tested before backup restoration is called reliable.

On Android, full reconciliation re-downloads every note and compares text rather than revisions: a note whose text matches is adopted at the server's revision; one the server lost or holds an older text of is re-sent; one the server no longer has is re-created. Progress is stored (`full_sync`, `full_sync_seen`), so it survives the app being killed halfway. One gap remains until the server marks restores: a note edited on the restored server whose revision is still below the device's is overwritten by the device's re-upload.

### 11.5 Health monitoring

`/healthz` confirms the process is running and `/readyz` that the database is reachable. Neither exposes application data; both work with systemd, Gatus, Uptime Kuma and similar tools.

### 11.6 Resource efficiency

- Avoid long-lived per-device connections, permanent background workers, in-memory copies of the database, full histories, external dependencies and polling jobs that scan every note.
- Keep transactions short, indexes limited to listing, sync and search, and skip Markdown parsing on reads.
- Sync transfers only changed notes, each in full, with HTTP compression where useful; diffs are excluded from V1.
- Tune and test the Go runtime on memory-constrained systems.
- Future attachments live outside note content, possibly content-addressed for deduplication and integrity.

## 12. Testing Strategy

Testing emphasizes failure scenarios over happy paths, with multiple simulated clients running independently against a shared server.

### 12.1 Synchronization scenarios

| Scenario | Expected result |
| --- | --- |
| Single device edits | Successful sync |
| Two devices edit different notes | Both changes preserved |
| Two devices edit different fields | Safe merge |
| Two devices edit content | Conflict copy |
| Request succeeds, response lost | Idempotent retry |
| Client crashes during download | Resumes without skipping changes |
| Client crashes during conflict handling | Pending edits preserved |
| Note deleted on another device | Tombstone applied |
| Deleted note edited offline | Recovered copy |
| Offline deletion conflicts with newer edit | Newer content preserved |
| Device offline for months | Successful sync |
| Server restored from backup | Safe reconciliation |
| Same note edited during upload | Later edits stay pending |

Property-based, randomized tests should generate arbitrary sequences of edits, deletions, disconnects, retries and reconnects, then assert that no unsynced user content disappears silently.

### 12.2 Other suites

- **Backend** (temporary SQLite databases): note CRUD, revision conflicts, deletions, transaction rollback, sequence allocation, pagination, search indexing, duplicate operation IDs, migrations, authentication.
- **Editors** (shared fixtures across web, iOS and Android): formatting selections, including across paragraphs; lists; nested formatting; undo/redo; cursor preservation; Markdown round trips; Unicode, emoji and right-to-left text; multiline selections; IME composition.
- **Performance** (thousands to tens of thousands of notes, on modest hardware): idle memory, startup time, note create and read latency, large-collection sync, search latency, database growth, mobile battery impact.
